# Pronunciation checks and fixes for synthetic English speech (state as of November 2026)

Scope: checking that a Breeze TTS 2 take says each word, and above all each invented or French-derived name, the way it should, keeping a recurring name the same across takes, voices and chapters, and fixing what is found when the TTS takes plain text. Dropped or repeated words, prosody, loudness and artifacts are out of scope (other researchers).

Metric note for the whole file: ZIPA and POWSM report PFER (phonetic feature error rate, an articulatory-feature edit distance), not PER. PFER is lower than PER for the same output because a near-miss substitution costs only the features that differ. Numbers from different papers are not on the same evaluation setup.

## 1. State of the art in mispronunciation detection and phoneme recognition (2024 to 2026), and whether it is accurate enough to compare a take against a dictionary or G2P reference

### Takeaway
Universal IPA phone recognizers became much better in 2025: ZIPA (May 2025, 64M to 300M params, ONNX FP32/FP16/INT8 exports, CC BY 4.0) reaches PFER of about 0.7 to 2.2 on clean read English (LibriSpeech), several times lower than wav2vec2-lv-60-espeak-cv-ft (2021, 300M, Apache-2.0) and Allosaurus (2020, 11M, GPL-3.0). They are accurate enough on clean synthetic speech to check a name, but a raw phone-string diff against a G2P reference will still raise false alarms from reduced vowels and dictionary-versus-speech mismatch, so a check should score the expected pronunciation against explicit alternatives (likelihood ratio or feature-weighted distance) rather than count raw phone edits.

The authors attribute this to training on G2P-derived dictionary transcriptions and say the models "smooth out" some variation. ([arXiv 2505.23170](https://arxiv.org/html/2505.23170v1))

ONNX inference needs onnxruntime, soundfile, librosa, lhotse and torch. Code is MIT, most models CC BY 4.0, the `ns` models CC BY-NC-SA 4.0 because of MMS-ulab v2 data. No speed numbers are given. ([GitHub lingjzhu/zipa](https://github.com/lingjzhu/zipa))
- POWSM (Oct 2025, revised Jan 2026, ACL 2026) is a 350M attention encoder-decoder (E-Branchformer encoder, Transformer decoder, hybrid CTC/attention, OWSM v3.1 style) trained from scratch on IPAPack++ that does phone recognition, ASR, and audio-guided G2P and P2G. On LibriSpeech it reports PFER 2.85 against 1.40 for ZIPA-CR-NS-Large, 6.89 Allosaurus, 7.70 Wav2Vec2Phoneme (the XLS-R fine-tune). On out-of-domain English (Buckeye, DRC-SE, L2-ARCTIC, EpaDB, speechocean762) the averages are Wav2Vec2Phoneme 12.89, ZIPA-CR-NS-Large 14.34, POWSM 14.40. Checkpoint at huggingface.co/espnet/powsm. ([arXiv 2510.24992](https://arxiv.org/html/2510.24992v2))

The setups differ, so compare only within a table. ([arXiv 2505.23170](https://arxiv.org/html/2505.23170v1), [arXiv 2510.24992](https://arxiv.org/html/2510.24992v2))
- POWSM audio-guided G2P on Buckeye: phone recognition 12.63, G2P from speech prompt only 12.71, speech plus text prompt 16.38, text prompt only 23.44. Adding the text prompt made the output worse against what was said. ([arXiv 2510.24992](https://arxiv.org/html/2510.24992v2))
- wav2vec2-lv-60-espeak-cv-ft: wav2vec2-large-lv60 fine-tuned on Common Voice to output multilingual phonetic labels, 16 kHz input, paper "Simple and Effective Zero-shot Cross-lingual Phoneme Recognition" (Xu, Baevski, Auli, Sept 2021), Apache-2.0. The output is a space-separated string of IPA-style labels with no words. ([Hugging Face model card](https://huggingface.co/facebook/wav2vec2-lv-60-espeak-cv-ft))
- For a reference point on 39-phone English, wav2vec 2.0 LARGE LV-60k fine-tuned on TIMIT reached 7.4 dev / 8.3 test PER. ([arXiv 2006.11477](https://arxiv.org/abs/2006.11477))
- Allosaurus: GPL-3.0, latest universal model `uni2005` (May 2020), English model `eng2102`, English inventory via `--lang eng`, phone priors via `prior.txt`, approximate CTC timestamps, CPU by default, no speed claims. ([GitHub xinjli/allosaurus](https://github.com/xinjli/allosaurus))
- Goodness of pronunciation with CTC models: Cao, Fan, Svendsen and Salvi (Interspeech 2024) proposed a GOP framework for CTC-trained models that needs no speech-phoneme alignment, is robust to alignment errors, and models deletions and insertions, beating the alignment-based baseline. ([papers.cool listing of cao24b](https://papers.cool/venue/cao24b@interspeech_2024@ISCA))
- Follow-up "Segmentation-free Goodness of Pronunciation" (arXiv July 2025, revised Feb 2026, accepted to IEEE TASLPRO, DOI 10.1109/TASLPRO.2026.3654852) defines GOP-SA (self-aligned) and GOP-SF (sums over all segmentations of the canonical transcription, with a normalization for model peakiness), evaluated on CMU Kids and speechocean762, claiming state of the art phoneme-level assessment on speechocean762. The abstract page gives no numbers and no code link. ([arXiv 2507.16838](https://arxiv.org/abs/2507.16838))
- Parikh et al. (Interspeech 2025) extend alignment-free CTC GOP by restricting substitutions to phoneme clusters and common learner errors. ([ISCA archive](https://www.isca-archive.org/interspeech_2025/parikh25_interspeech.html))
- Standard MDD pipelines recognize phones and align the output with the canonical sequence (often LCS or edit distance) to locate substitutions, insertions and deletions. A 2025 Speech Communication paper uses wav2vec2 phonological-attribute detection to describe which articulators are wrong. ([arXiv 2311.07037](https://arxiv.org/pdf/2311.07037), [Mandarin attribute MDD, arXiv 2606.22022](https://arxiv.org/abs/2606.22022))
- Closest published TTS-side check: say-it-right (MIT, split out of OpenMontage on 2026-11-10, 5 commits, no tags) runs three CPU ears on each TTS take: Whisper `small.en` for words, `facebook/wav2vec2-large-960h-lv60-self` character CTC with no language model for letters, and `facebook/wav2vec2-lv-60-espeak-cv-ft` for IPA phones, compared to a researched IPA per hard word with a "feature-weighted, accent-tolerant distance". Models take about 3.5 GB on disk, PyTorch CPU, no GPU. ([GitHub say-it-right](https://github.com/logitsolutionsai/say-it-right))
- say-it-right results: on its own 32 reads of 8 hard names with 2 voices, correct reads passing went from 8/22 (old transcript check) to 22/22, with 10/10 wrong reads caught, which the author calls "a fit, not a test". On speechocean762 (2,500 non-native utterances, 15,967 words) word-level detection reached ROC-AUC 0.843 against 0.788 for plain phone error rate (0.858 against 0.838 for words of two or more syllables). On learner speech it flags 27% of words and catches 78% of expert-marked wrong words. A short take is checked in 3 to 4 s on a laptop CPU with models loaded. ([DEV Community post](https://dev.to/logitsolutionsai/speech-to-text-cant-tell-you-if-an-ai-voice-said-a-name-right-5bge))
- Vox-Evaluator (Tencent AI Lab authors, arXiv Oct 2025, CC BY-NC-ND paper, no code, demo only): a 185M evaluator (wav2vec 2.0 style 6-layer speech encoder, BART-style unit encoder and text decoder, BiLSTM timestamp head) that takes the synthesized speech and the target text as phoneme tokens and outputs error segment boundaries and a quality score. Training data FGES has about 22k F5-TTS and VoiceCraft samples labelled by Whisper-large-v3 diff plus MFA timestamps. Error localization IoU 0.782 against 0.653 for fine-tuned wav2vec 2.0. Masking and regenerating the flagged segments cut WER on Seed-TTS test-en from 1.73 to 1.42 (F5-TTS) and 7.56 to 5.11 (VoiceCraft). ([arXiv 2510.20210](https://arxiv.org/abs/2510.20210), [HTML](https://arxiv.org/html/2510.20210))

### Inferences
- For audiogen the best fit is ZIPA-CR small (64M, CTC, ONNX INT8) on CPU in the audio Python with onnxruntime, with wav2vec2-lv-60-espeak-cv-ft as the fallback that has a known TTS-name use (say-it-right). ZIPA-CR is CTC, which means no internal phone LM, and it is the most accurate on clean read English. The NS variants are non-commercial, which fits a hobby pipeline. ZIPA's ONNX path imports torch and lhotse, so it may need a trimmed loader to fit the existing audio Python.
- On clean single-speaker TTS audio, PFER around 1 means the recognizer itself rarely invents a phone change. Most false alarms will then come from the reference: espeak-ng or CMUdict give citation forms with full vowels, while connected speech reduces them, and a name's "right" pronunciation is a decision, not a dictionary fact. Hence score a name against a short list of intended and competing pronunciations, not against one G2P string.
- The ZIPA dictionary-smoothing finding and the POWSM text-prompt result point the same way: anything trained on G2P labels or conditioned on the text drifts toward the canonical form. A pronunciation check should use free phone decoding or likelihood scoring with no text prompt, from a CTC model.
- say-it-right's 27% flag rate on learner speech is too strict for raw use, but TTS voices make far fewer accent-level slips, and a false alarm in audiogen costs only a retake with a new seed. The retake budget, not the listener, absorbs false alarms.
- Vox-Evaluator's fix (mask and regenerate the segment) needs an editing TTS. Breeze TTS 2 has no documented segment infill, so in audiogen the fix for a flagged name is a whole-line retake or a best-of-N pick.

### Gaps
- No published PER or PFER of any phone recognizer on modern zero-shot TTS output, and no benchmark of name mispronunciation in TTS (say-it-right notes that no public TTS-name benchmark exists).
- No CPU speed numbers for ZIPA ONNX models. Whether sherpa-onnx can load ZIPA's CTC ONNX export directly (it is an icefall Zipformer) was not verified.
- POWSM's model licence and ZIPA's exact model-card release dates were not found.
- The full text of Cao et al. 2024 and GOP-SF, with their numbers, was not read.

## 2. Why a word recognizer hears through a mispronunciation, and what makes a check stricter

### Takeaway
A word recognizer is trained to output the most likely written word, through a subword vocabulary and, in transducers like Parakeet TDT, a prediction network that acts as an internal language model, so a near-miss reading of a known word comes out spelled correctly and an invented name comes out in the recognizer's own spelling either way. A check gets stricter as it removes priors: character CTC with no LM, then phone CTC with no LM, then forced-alignment likelihood of the expected phones against competing pronunciations, which is the GOP family.

### Cited Findings
- "A speech-to-text model is trained to write likely text", so near-miss pronunciations get transcribed as the correct spelling, while correct reads of unknown names get spelled differently and fail. The old transcript check passed only 8 of 22 correct reads of hard names. ([DEV Community post](https://dev.to/logitsolutionsai/speech-to-text-cant-tell-you-if-an-ai-voice-said-a-name-right-5bge))
- say-it-right adds a character-level recognizer "without a language model" specifically "to catch slips the first one smooths over", and a phone ear for what both miss. In their example a name that should be /ʃ ɪ v ɔ n/ was said /j ɑ b ə n/ and only the phone check caught it. ([DEV Community post](https://dev.to/logitsolutionsai/speech-to-text-cant-tell-you-if-an-ai-voice-said-a-name-right-5bge), [GitHub](https://github.com/logitsolutionsai/say-it-right))
- In RNN-T style end-to-end models the prediction and joint networks learn an internal language model, which can be estimated and subtracted (ILME). ([Meng et al., arXiv 2011.01991](https://arxiv.org/abs/2011.01991))
- Conventional ASR language models "are likely to perform auto-correction", so distortions and substitutions go unrecognized. A Whisper base.en study found it tends to output near-homophones, which makes it unsuited to pronunciation error detection. ([search summary of child-speech and thesis sources, thesis PDF](https://home.cltl.labs.vu.nl/static/data/theses/thesis_Furong_Zou_2024.pdf), [arXiv 2403.08187](https://arxiv.org/pdf/2403.08187))
- Traditional GOP needs a phone-to-speech alignment and cannot express deletions or insertions. CTC-based GOP that considers all segmentations of the canonical phones is robust to alignment errors. ([Cao et al. 2024 listing](https://papers.cool/venue/cao24b@interspeech_2024@ISCA), [arXiv 2507.16838](https://arxiv.org/abs/2507.16838))
- WhisperPPT, an autoregressive phone recognizer, can hallucinate repeated substrings, and ZIPA-T (transducer) has a prediction network, while ZIPA-CR is pure CTC. ([arXiv 2505.23170](https://arxiv.org/html/2505.23170v1))
- NVIDIA's heteronym labeling pipeline generates candidate pronunciations for each heteronym and scores them with a RAD-TTS Aligner, which is the "score the candidates with an aligner" pattern applied to real speech. ([arXiv 2302.14523](https://arxiv.org/abs/2302.14523))

### Inferences
- Parakeet TDT 0.6B v2 is a token-and-duration transducer over subword tokens, so it carries an internal LM and English spelling priors. That explains both behaviours in audiogen: it hears "Lewis" in a misread "Louis" as a plausible word, and it spells invented names its own way, which is why WER over 0.34 is only "suspect" today.
- Stricter check, in order of cost and strength, for one name span:
  1. Free phone decoding (ZIPA-CR or wav2vec2-espeak greedy CTC) of the span, then a feature-weighted edit distance (for example panphon, [GitHub dmort27/panphon](https://github.com/dmort27/panphon)) to the intended IPA.
  2. CTC likelihood ratio: compute the CTC log-likelihood of the intended phone sequence and of each competing pronunciation (the known misreadings, the espeak-ng reading of the raw spelling, the LLM's alternatives) over the span, and pass only when the intended one wins by a margin. This is GOP-SF style scoring and is robust to small G2P differences that are not on the list.
  3. Accept only when both agree, and send everything else to a retake.
- The span can come from Parakeet word timestamps of the take, or from CTC forced alignment of the whole line's expected phones, so the name is scored in its context with no separate segmentation model.
- Because a phone CTC model has no word prior, it cannot "hear through" a name it has never seen, which is the case the current Parakeet check cannot handle.

### Gaps
- No study found that measures how often Parakeet specifically transcribes a mispronounced name as the right word.
- No published thresholds for CTC likelihood-ratio pronunciation checks on TTS audio. They would have to be calibrated on audiogen's own takes.

## 3. Checking that a recurring invented name is said the same way every time

### Takeaway
No paper or tool was found that checks name consistency in TTS output across takes, voices and chapters, so this has to be assembled from query-by-example spoken term detection: phone posteriorgrams with DTW are the classic speaker-independent way to compare two spoken instances of one word, self-supervised acoustic word embeddings are a cheaper alternative, and comparing each occurrence's phone string or posteriorgram with one canonical rendering is the simplest workable design. One 2026 research model (GRAFT) conditions a codec-LM TTS on a spoken example of a word, which would fix consistency at the source, but it has no code.

### Cited Findings
- Posteriorgrams exist to represent speech in a speaker-independent form while keeping phonetic information, and are matched with DTW in query-by-example search. State-of-the-art QbE relied on DTW template matching over DNN phone posteriors. ([MIT thesis PDF](https://dspace.mit.edu/bitstream/1721.1/79217/2/844753073-MIT.pdf), [EPFL thesis](https://infoscience.epfl.ch/entities/publication/1bc6c09d-8b61-4890-8df3-dd3f9ada3d11/thesisdetails))
- A 2025 APSIPA paper trains a model to output posterior vectors of speaker-independent units such as phonemes and matches query and utterance posteriorgrams with continuous DP (DTW applied continuously), with CTC training for phoneme-level representations. ([APSIPA 2025 P142](https://webdev.apsipa.org/proceedings/2025/papers/APSIPA2025_P142.pdf))
- DTW over a speaker-independent posteriorgram space was used for similarity search at Interspeech 2017, and a distinctive-feature posteriorgram front end at Interspeech 2015. ([Interspeech 2017](https://www.isca-archive.org/interspeech_2017/gundogdu17_interspeech.html), [Interspeech 2015](https://www.isca-archive.org/interspeech_2015/saxena15_interspeech.pdf))
- Acoustic word embeddings: Settle et al. (2017) found neural AWEs with nearest-neighbour search beat DTW on accuracy and run time for QbE. Self-supervised frame features (CPC, APC, wav2vec 2.0, XLSR-53) beat MFCCs as input. Pooling pre-trained HuBERT or wav2vec 2.0 layers gives usable AWEs, and HuBERT and wav2vec 2.0 beat XLSR-53 there. Pasad et al. (2024) confirmed pooled self-supervised AWEs are effective and carry some semantic information. One low-resource study found DTW still state of the art in its setting. ([arXiv 1706.03818](https://arxiv.org/pdf/1706.03818), [arXiv 2308.14905](https://arxiv.org/pdf/2308.14905), [arXiv 2401.10543](https://arxiv.org/html/2401.10543v2))
- GRAFT (arXiv July 2026): per-word pronunciation conditioning for neural codec language-model TTS. A short spoken sample of the word is encoded with the model's own speech tokenizer and bound to the word's position in the prompt. Voice conversion in data construction lets the sample come from any speaker while the output keeps the target voice. Target-word PER fell 22 to 39% against the same text-only backbone over five languages, and an English listening test ranked it first. No code is stated. ([arXiv 2607.02633](https://arxiv.org/abs/2607.02633))
- GRAFT's authors argue that neural phone recognisers such as ZIPA and Wav2Vec2-Phoneme learn acoustic-to-phonetic mappings, which is why a spoken example can stand in for phonetic notation. ([arXiv 2607.02633 PDF](https://arxiv.org/pdf/2607.02633))
- Practitioner sources on AI audiobooks say pronunciation consistency of character names is harder than voice quality and fix it with a pronunciation list plus regenerating affected sections, not with automatic consistency checks. ([Narration Box guide](https://narrationbox.com/blog/pronunciation-consistency-harder-than-voice-quality-audiobook-guide), [Narration Box names guide](https://narrationbox.com/blog/how-to-fix-mispronounced-character-names-ai-audiobook))

### Inferences
- Speaker independence matters because the same name is spoken by several cloned voices. Phone posteriorgrams from a CTC phone recognizer (ZIPA-CR or wav2vec2-espeak) are designed to drop speaker identity, while pooled HuBERT or wav2vec 2.0 AWEs keep more speaker and channel information. For audiogen, posteriorgram DTW or plain phone strings are the safer choice across voices.
- A workable design with no new model:
  1. Pick a canonical rendering per name, the winner of the respelling audition in section 6, stored as its phone string and its posteriorgram.
  2. For every take that contains the name, cut the span (Parakeet word timestamps or CTC alignment of the line), decode its phone string, and compute both the feature-weighted distance and the DTW distance of its posteriorgram to the canonical.
  3. Keep a per-name running list across chapters. Flag a take whose distance is an outlier against that name's history (for example above the 95th percentile of past accepted occurrences) or whose phone string falls in a different cluster from the canonical (agglomerative clustering on feature-weighted edit distance).
  4. Fix by retaking the line with new seeds and keeping the take closest to the canonical, which is a best-of-N selection with a consistency score.
- Clustering occurrences also finds drift that no single-take check sees: if two clusters appear for one name across chapters, the say-as entry or the voices disagree, and the cluster that matches the intended IPA wins.
- GRAFT-style conditioning on a canonical clip would be the real fix, but Breeze TTS 2 has no such input, so this stays a watch item.

### Gaps
- No reported accuracy for detecting inconsistent name pronunciations across TTS voices with any of these methods. Thresholds and the false-alarm rate would have to be measured on audiogen's own takes.
- No 2024 to 2026 benchmark comparing posteriorgram DTW and AWEs across synthetic voices was found.

## 4. Heteronyms, numbers, abbreviations and symbols before synthesis

### Takeaway
English heteronym disambiguation is a solved-enough classification problem when labelled data exists (per-homograph classifiers on contextual embeddings reach 0.991 on the public WikiHomograph data), and LLMs now both generate such data and do G2P in context, while LLM-based text normalization is the documented fix for numbers, abbreviations, URLs and units in LLM-based TTS. For a plain-text TTS like Breeze, the practical route is to let the Claude screenplay pass normalize numbers and symbols to words and tag heteronym senses, then respell the rarer sense, and to verify the chosen variant on the take with a two-way likelihood test.

### Cited Findings
- WikiHomograph (Google, Gorman et al. 2018) is described as the only open English dataset large enough to train a neural heteronym model, with one labelled heteronym per sentence, but it lacks full coverage of English homographs. NeMo extracts heteronym forms from WikipediaHomographData and ships an export script. ([arXiv 2302.14523](https://arxiv.org/pdf/2302.14523), [NeMo G2P docs](https://docs.nvidia.com/nemo-framework/user-guide/25.09/nemotoolkit/tts/g2p.html), [GitHub google-research-datasets/WikipediaHomographData](https://github.com/google-research-datasets/WikipediaHomographData))
- Nicolis and Klimkov (ISCA SSW 2021): per-homograph classifiers on contextual word embeddings reached 0.991 accuracy on the public English homograph data, and about 100 balanced sentences suffice to train a light classifier. ([ISCA SSW 2021](https://www.isca-archive.org/ssw_2021/nicolis21_ssw.html))
- NVIDIA (Huang, Bakhturina, Tatanov, Feb 2023) label heteronyms in audio-text data automatically by scoring candidate pronunciations with a RAD-TTS Aligner, to feed G2P training. ([arXiv 2302.14523](https://arxiv.org/abs/2302.14523))
- GPT-4 with in-context knowledge retrieval for G2P improved Librig2p by 3.5% absolute (3.8% relative). ([arXiv 2411.07563](https://arxiv.org/pdf/2411.07563.pdf))
- "Fast, Not Fancy" (EMNLP 2025 Findings) used LLMs to build HomoRich, 528,891 Persian sentences over 285 homographs, and added a light statistical model to eSpeak for a 30.66% improvement in homograph disambiguation at real-time speed. The LLM made the data, not the runtime decision. ([arXiv 2505.12973](https://arxiv.org/html/2505.12973v1))
- PhonologyBench (2024) found LLMs below human annotators on English G2P. A June 2026 Japanese G2P benchmark found the best API models under 0.6% kana CER but named proper nouns as a major unmeasured error source. OLaPh (2025) applies NER and language-specific rules to names before phonemizing. ([search summary, PhonologyBench arXiv 2404.02456](https://arxiv.org/pdf/2404.02456v2.pdf), [arXiv 2606.22009](https://arxiv.org/pdf/2606.22009), [OLaPh arXiv 2509.20086](https://arxiv.org/html/2509.20086v1))
- EmergentTTS-Eval (Boson AI, May 2025): 1,645 samples in six categories. Homographs sit under Syntactic Complexity, and Complex Pronunciation covers emails, phone numbers, URLs, addresses, STEM equations, units, abbreviations and tongue twisters. Poor Complex Pronunciation is a systematic failure of most open models and ElevenLabs, and LLM-based text normalization significantly improves it. Data on Hugging Face `bosonai/EmergentTTS-Eval`, code `boson-ai/EmergentTTS-Eval-public`. ([arXiv 2505.23009](https://arxiv.org/pdf/2505.23009), [Moonlight review](https://www.themoonlight.io/review/emergenttts-eval-evaluating-tts-models-on-complex-prosodic-expressiveness-and-linguistic-challenges-using-model-as-a-judge))
- CosyVoice 3 reports "pronunciation inpainting" tests on hard Chinese polyphones and English polyphonic words, with a best correction rate of 100%, and the released Fun-CosyVoice3-0.5B-2512 supports Chinese pinyin and English CMU phonemes in the text. ([arXiv 2505.17589](https://arxiv.org/pdf/2505.17589), [model card mirror](https://huggingface.co/zhchhe/Fun-CosyVoice3-0.5B-2512))
- The Breeze-TTS-2.cpp tokenizer applies no normalization: it maps spaces to the SentencePiece meta symbol, matches special tokens, and runs Gemma BPE with byte fallback on the raw text. The sentence splitter only splits. (verified locally in `D:\comfy\breeze-cpp\src\src\tokenizer.cpp` and `src\text_split.cpp`, v0.1.6, and `docs\architecture.md` "Gemma BPE tokenizer", [GitHub HoppouAI/Breeze-TTS-2.cpp](https://github.com/HoppouAI/Breeze-TTS-2.cpp))

### Inferences
- Breeze reads digits, symbols and abbreviations however its training taught it, with no front end in between. The cheapest fix is in the Claude screenplay pass (prompt rule: spell out numbers, ordinals, units, roman numerals and abbreviations as spoken words) plus a deterministic pre-render lint that flags any digit, `%`, `&`, `/`, roman numeral or all-caps token left in a line. This is a text-side check with zero false alarms and no audio cost.
- Heteronyms: the screenplay pass already reads the whole chapter, so it can tag each heteronym occurrence with its sense (read/past, lead/metal, wind/verb, bow/weapon, tear/rip) at little extra cost. The fix in a plain-text TTS is a respelling of the less frequent sense where an unambiguous spelling exists (lead as "led", read as "red", tear as "tare", bow as "boh"), applied per occurrence, not per serial as today's say-as map does.
- Verification of a heteronym on the take is a two-way decision, which suits the CTC likelihood-ratio test in section 2: score /ɹiːd/ against /ɹɛd/ over the word span. Two known alternatives make this far more reliable than a free decode against a G2P string.
- A wrong heteronym reading may vary by seed in a sampled LLM-TTS (temperature 0.9), so a retake may fix it before a respelling is needed. This is unmeasured for Breeze.

### Gaps
- No English homograph benchmark result for 2025 or 2026 LLMs (Claude, GPT) was found, and no measurement of how often LLM-based TTS models like Breeze misread heteronyms.
- How Breeze TTS 2 reads digits, abbreviations and symbols was not tested or documented anywhere found.

## 5. Production pronunciation features, respelling a zero-shot TTS, and whether Breeze TTS 2 takes phonemes

### Takeaway
Commercial services all use lexicons with two rule types, an alias (a respelling) and a phoneme (IPA or a vendor alphabet), but phoneme rules work only on models built with a phoneme path: ElevenLabs states its dictionary phoneme tags work only on eleven_v4, eleven_v4_turbo, eleven_flash_v2 and eleven_v3, and other models fall back to alias rules. Breeze TTS 2 (BreezeBlue, 3B, weights released 2026-08-25) documents no phoneme, IPA or SSML input, and its C++ port tokenizes raw text with Gemma BPE, so respelling is the only text lever, and a few 2025 and 2026 open models (CosyVoice 3, GLM-TTS) are the ones that accept phonemes inline.

### Cited Findings
- Breeze TTS 2 model card: 3B params, English and Chinese, weights and PyTorch code released 2026.08.25, weights under the BreezeBlue Research and Non-Commercial License, code Apache-2.0, audio tokenizer based on Qwen3-TTS. Modes are Voice Clone (reference audio plus exact transcript), Voice Design (natural-language description) and Voice Direction. No phoneme, IPA, respelling or name guidance is mentioned. ([Hugging Face BreezeBlue/Breeze-TTS-2](https://huggingface.co/BreezeBlue/Breeze-TTS-2))
- Breeze TTS 2 inline markup is only vocal-event cues: parentheses in English such as `(laugh)`, `(cough)`, `(clears throat)`, `(sigh)`, square brackets in Chinese. The official repo also documents `seed`, `--cfg-scale 4` for stronger instruction following, and `repetition_penalty=1.1`. ([GitHub breezeblue-ai/breeze-tts](https://github.com/breezeblue-ai/breeze-tts))
- Breeze-TTS-2.cpp: C++/GGUF reimplementation with `POST /v1/audio/speech` taking `text`, `instruction`, `voice_id`, a WebSocket API, and a "free form" event tag vocabulary. No phoneme, IPA or SSML input. ([GitHub HoppouAI/Breeze-TTS-2.cpp](https://github.com/HoppouAI/Breeze-TTS-2.cpp))
- Local v0.1.6 source (verified): tokenizer is "Gemma BPE with byte fallback" (`docs\architecture.md`), default sampling temperature 0.9 and top-k 50 from the GGUF (`docs\models.md`, `src\config.cpp`), and the server takes per-request `seed` (default 42) and `temperature` fields where 0 keeps the GGUF value (`docs\server.md` lines 265 and 266). `docs\cli.md` says the seed fully determines the output for a given model and input.
- ElevenLabs pronunciation dictionaries: PLS-style XML lexemes with grapheme and phoneme, IPA and CMU alphabets, case sensitive (list both "tomato" and "Tomato"), attached per request by `pronunciation_dictionary_locators`. "Pronunciation dictionary phoneme tags only work with eleven_v4, eleven_v4_turbo, eleven_flash_v2 and eleven_v3 models. Other models skip dictionary phoneme tags and use the default pronunciation", and for those the docs recommend alias tags. ([ElevenLabs docs](https://elevenlabs.io/docs/eleven-api/guides/how-to/text-to-speech/pronunciation-dictionaries))
- Azure custom lexicon: up to 100 KB per file (split into several if larger), case sensitive, alias wins over phoneme for the same grapheme, phrases need an alias plus a phoneme, cached by URI, must be reachable by URL (Blob plus SAS is fine). ([Microsoft Learn](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/speech-synthesis-markup-pronunciation))
- Amazon Polly lexicons: up to 40,000 characters each, larger lexicons add latency, each phoneme or alias replacement up to 100 characters, applied outside SSML (the `<lexicon>` tag is unsupported), inline `<phoneme>` is supported. ([AWS Polly quotas](https://docs.aws.amazon.com/polly/latest/dg/limits.html))
- Respelling is described by vendors as a stopgap and fragile: a respelling that works on one model may fail on the next. ([Soniox wiki](https://soniox.com/wiki/pronunciation-control-ssml), [Picovoice blog](https://picovoice.ai/blog/custom-pronunciation-in-tts/))
- LLM respelling as TTS input (Hitachi, arXiv March 2026): GPT rewrites words in the same orthography ("Bo-in" for Boeing, "Jang" for Zhang, "eer-kraft" for aircraft) and feeds kokoro-TTS. The paper measures only downstream ASR WER and never checks how the TTS actually read the respellings. ([arXiv 2603.16920](https://arxiv.org/html/2603.16920))
- GLM-TTS (Zhipu, open-sourced 2025-12-11, Apache-2.0): optional phoneme mode with G2P, then a dictionary replacement of target words' phonemes, then a hybrid phoneme-and-text input. It primarily supports Chinese with English mixed text. ([GitHub zai-org/GLM-TTS](https://github.com/zai-org/GLM-TTS))
- CosyVoice 3 compares phoneme schemes: "CatPhn" keeps the characters and attaches phonemes, "MixPhn" replaces the characters by phonemes, and MixPhn stays hard to make competitive. ([arXiv 2505.17589](https://arxiv.org/pdf/2505.17589))
- SonoEdit (arXiv Jan 2026): a one-shot closed-form weight edit of an LLM-based TTS that steers a proper noun toward a pronunciation exemplar while leaving other behaviour unchanged. The abstract page gives no numbers, base model or code. ([arXiv 2601.17086](https://arxiv.org/abs/2601.17086))
- Audiobook proofing tools: Pozotron compares audio with the script and flags misreads, missed and added words, and its Script Sync feeds a pronunciation guide and character profiles into proofing. Narration Box recommends a pronunciation list of every recurring name, saved rules where supported, and regenerating only the affected sections. No independent accuracy figures were found. ([Pozotron proofing](https://www.pozotron.com/proofing), [Pozotron Script Sync](https://blog.pozotron.com/maximize-efficiency-with-pozotrons-script-sync), [Narration Box](https://narrationbox.com/blog/how-to-fix-mispronounced-character-names-ai-audiobook))
- Cloud checking alternative: Azure Pronunciation Assessment takes a reference text and returns word and phoneme scores with `NBestPhonemeCount` alternatives (SAPI alphabet in the examples) and is billed like speech to text. A November 2025 Microsoft Q&A answer gives about $1.32 per audio hour for standard real time, and a third-party page lists $1 per hour. Official pricing pages showed placeholders, so this is unverified. ([Microsoft Q&A pricing](https://learn.microsoft.com/en-us/answers/questions/5608069/pricing-and-usage-of-pronunciation-assessment-feat), [how-to](https://learn.microsoft.com/en-ca/azure/ai-services/speech-service/how-to-pronunciation-assessment))

### Inferences
- Breeze tokenizes Gemma BPE pieces of the raw string, so a respelling works only through the grapheme-to-sound habits the model learned from English text. Common-word respellings ("Lewis", "Laurie Anne") have well-trained sounds, while hyphenated or capitalized pseudo-spellings are less predictable, which is why every respelling needs an audio check rather than trust.
- Parentheses are Breeze's vocal-event syntax with a free-form vocabulary, so a respelling or a script line must never put a name inside parentheses, or the name may be performed as a sound event.
- IPA characters would reach the model as byte-fallback tokens it almost certainly never saw in training, so passing IPA in the text is not a viable lever. This is inference from the tokenizer code, not a test.
- Since the server takes a per-request `temperature`, a lower temperature for lines that carry a hard name is a cheap lever to cut seed-to-seed pronunciation variance. Untested, and it may flatten delivery.
- Cost of the Azure check per finished hour, if every take is checked once: about 1 hour of audio plus retakes, so roughly $1.1 to $1.7 per finished hour at the quoted rates. Checking only name-bearing spans would cost a fraction. Azure's English G2P would still have to be given a usable reading of invented names, which needs its own lexicon.

### Gaps
- Breeze TTS 2's training front end (whether the training text was normalized, whether names were seen) and its default behaviour on IPA input are undocumented.
- No published measurement of how reliably respelling steers any zero-shot LLM-based TTS.
- No detail found on ElevenLabs Studio or Audible-style audiobook proofing beyond vendor descriptions.

## 6. Prior art for building the pronunciation dictionary automatically (LLM proposes, TTS renders, phone recognizer scores, most stable respelling wins)

### Takeaway
No published system closes the whole loop for TTS. The pieces exist separately: say-it-right (Nov 2026) checks TTS takes of researched names against IPA with a phone recognizer but expects a human to research the pronunciation and write the respelling, NVIDIA scores candidate heteronym pronunciations with an aligner, older Facebook and patent work uses TTS output and ASR checks to learn pronunciations, and Hitachi uses an LLM to write respellings for TTS. The proposed loop is new in combination but every step has a cited precedent.

### Cited Findings
- say-it-right's workflow is: find risky words, research each one (its `vc lookup` draws on Wikipedia, Wikidata, Wiktionary, Commons and VOA candidates), store respelling, IPA and source in a YAML lexicon, render with the engine's syntax (text, ElevenLabs, Cartesia, Kokoro, Piper, SSML), then check every take. It exports PLS for ElevenLabs, Azure and Polly. Words missing from the lexicon get only the word and letter checks. ([GitHub say-it-right](https://github.com/logitsolutionsai/say-it-right), [DEV Community post](https://dev.to/logitsolutionsai/speech-to-text-cant-tell-you-if-an-ai-voice-said-a-name-right-5bge))
- Candidate scoring by alignment: NVIDIA generates candidate pronunciations per heteronym and keeps the one a RAD-TTS Aligner scores best against the audio. ([arXiv 2302.14523](https://arxiv.org/abs/2302.14523))
- G2G (Facebook, 2019): TTS-driven pronunciation learning trains a grapheme-to-grapheme model from TTS data that rewrites rare names into homophone spellings, improving graphemic ASR on names. ([ResearchGate G2G](https://www.researchgate.net/publication/336868776_G2G_TTS-Driven_Pronunciation_Learning_for_Graphemic_Hybrid_ASR))
- Pronunciation learning from speech for contact names starts from a seed lexicon and learns new words' pronunciations from word-transcribed audio. ([ResearchGate](https://www.researchgate.net/publication/307889288_Learning_Personalized_Pronunciations_for_Contact_Name_Recognition))
- USPTO patents describe testing a TTS voice with ASR and, on a mismatch, adding a pronunciation variant from a list and running ASR again. ([US 8073694](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/8073694), [US 7742921](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/7742921))
- LLM respellings for TTS input are generated by GPT in the Hitachi work, with no audio check of the result. ([arXiv 2603.16920](https://arxiv.org/html/2603.16920))
- LLM G2P is below human annotators in English (PhonologyBench 2024), and proper nouns are named as a major unmeasured error source (2026 Japanese G2P benchmark), so an LLM's proposed IPA for a name is a proposal, not ground truth. ([arXiv 2404.02456](https://arxiv.org/pdf/2404.02456v2.pdf), [arXiv 2606.22009](https://arxiv.org/pdf/2606.22009))
- GRAFT and SonoEdit both take a pronunciation exemplar as the target, which shows the research direction is "say it like this clip" rather than phonetic notation. ([arXiv 2607.02633](https://arxiv.org/abs/2607.02633), [arXiv 2601.17086](https://arxiv.org/abs/2601.17086))

### Inferences
- A concrete loop for audiogen, run when the character bible gains a name, on the laptop for renders and CPU for scoring:
  1. Claude proposes the intended pronunciation in IPA with stress (using the serial's context, French origin and any in-text hints), two or three plausible misreadings, and 4 to 6 English respellings, with no parentheses.
  2. Breeze renders each respelling in 2 neutral carrier sentences ("The name was X." and a mid-sentence carrier) with 3 seeds in one cast voice. At the laptop's recorded 2.8 s per take, 6 respellings x 2 carriers x 3 seeds is 36 takes, about 100 s of GPU per name, which can run between chapters (the one-GPU-job rule still holds).
  3. The phone recognizer scores each take's name span: feature-weighted distance to the intended IPA and the CTC likelihood margin of the intended pronunciation over the misreadings.
  4. Keep the respelling with the best mean score and the smallest spread across seeds and carriers, then confirm it in each voice that speaks the name with one or two takes. Write it to the say-as map with its IPA and scores, and keep its best take as the canonical rendering for the consistency check in section 3.
  5. If no candidate passes, ask Claude for new respellings with the failing phone strings as feedback, which is the patent loop with an LLM in place of a fixed variant list.
- The plain respelling "Louis to Lewis" class of fix that AJ finds by ear today is exactly what step 4 would find without him, and his existing say-as entries are labelled examples to calibrate the thresholds on.
- For French-derived names the intended IPA should be an anglicized target the English-Chinese Breeze model can produce (for example no nasal vowels), and the multilingual IPA recognizers can still tell an anglicized reading from a spelling-pronunciation.
- The same recognizer output feeds three automatic fixes: retake with a new seed, best-of-N selection by score, and escalation to the next respelling when a name fails across seeds.

### Gaps
- No published end-to-end system or accuracy figure for an LLM-proposed, TTS-rendered, recognizer-scored respelling loop.
- No measured seed-to-seed pronunciation variance for Breeze TTS 2 or any LLM-based TTS on invented names, so the number of seeds needed per candidate is a guess.
- How often Claude's IPA for an invented fantasy name matches what the author or listener intends is unmeasured.
